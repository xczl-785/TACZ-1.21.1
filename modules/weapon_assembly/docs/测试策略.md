## 建议

保留普通 JVM 算法测试；交互与模型先在隔离 Minecraft 客户端测试；真实物品和射击随后做组合测试。独立指运行环境与夹具隔离，不是另做一套网页组装规则，也不是让测试界面拥有玩家库存。

项目已有两个可复用的组织方式：

- `source/integration-tests/external-consumer`：独立消费者工程，只依赖正式 Jar/公开能力，独立 client/server 目录；其 UI audit 可不进入世界。
- `tactical` 的 `uiAudit/modelDisplayAudit`：开发源集中的检查场景与截图，运行于隔离目录，代码不进入玩家 Jar。

具体选用哪一种，要看界面参考的框架依赖。优先在 `source/integration-tests/` 放薄的组装测试宿主，消费相同的正式组件和模型加载器；若沿用现有 UI 开发源集更直接，也可使用独立 run。二者都不复制算法与未来正式交互代码。当前不新建空宿主来提前锁定渲染方案。

## 隔离界面如何直接驱动

未来测试宿主提供固定的起始装配与一个只在内存中的“可选测试零件集合”。它调用同一个 AssemblyEngine，展示 `after/detached/errors`；这个集合明确属于开发夹具，不假装真实背包，也不持久化成第二份资产。

正式界面接收只读装配状态与操作回调。测试宿主实现回调时调用纯引擎；真实宿主实现回调时走服务器申请和库存事务，再推送最新状态。共用的是界面组件和装配规则，回调的提交方式根据宿主职责不同。这样替换测试宿主时不推翻界面。

若页面可在无玩家/无世界环境展示，优先主菜单后直接打开测试页；若模型渲染依赖世界或光照，使用专用测试世界。不能为了绕过依赖把客户端当成网页预览，也不能依赖日常世界里的特殊装备或管理员状态。

## 简易模型要检验什么

- 根模型与每个零件的原点、单位、坐标轴一致；子件按挂点相对父件安装，不能为每个完整组合手调世界坐标。
- 三层链逐层继承变换；转动整枪时所有零件跟随。
- 同型号两件共享模型资源，但拥有不同实例 ID/路径，选中、拆卸不串位置。
- 拆下父件，随它保留的子件一并离开枪；替换路线不会留下旧模型。
- 数据冲突由算法决定，不用几何碰撞推导兼容；测试低模可能夸张位置以便观察，不能当真实物理尺寸或瞄准校准。
- 空必需槽显示不完整状态；完成装配不代表已经满足弹药、枪膛、耐久或可射击条件。
- 自由旋转、缩放、窗口尺寸与 GUI 缩放分别检查；截图只证明当时画面，不代替连续操作。

Blockbench/OBJ 等离线预览是素材检查，只有经过所选游戏模型加载器再测试，才能确认游戏内兼容。格式转换脚本或挂点加载器的正式归属要在阅读界面工程和现有渲染入口之后决定。
